# 广告落地页 + WhatsApp 客服号池

解决的具体问题：FB 私信聊得动，但客户不肯跳到 WhatsApp；直接发号码也不跳。

原因不是"客户不愿意"，而是**跳过去成本太高**——要离开 FB、点开陌生号码、存联系人、再重说一遍自己要什么。这套方案只做一件事：把"跳过去"变成一次点击，而且跳过去的时候话已经替他说完了。

---

## 1. 两个页面，各管一件事

| 地址 | 用途 | 谁用 |
| --- | --- | --- |
| `/lp` | 广告落地页。全部 30 款产品、图片、分类，**不标价格** | 客户 |
| `/wh-admin` | 客服号池后台。加号、停号、权重、国家、每日上限、看每个号接到多少人 | 你 |

没有按产品分的落地页。所有广告都投 `/lp`，页面本身就是完整的商品目录。

### 落地页为什么不标价格

标了价格，客户会拿价格去比价、去别处问，然后就不聊了。不标价格，客户想知道多少钱就必须发一条消息——而这条消息就是线索。这也是同行那套（`ws.html`）的做法：产品图 + 规格 + "contact for special offers"，从头到尾没有数字。

价格、库存、运费、COA 全部在聊天里给，一次给全。

### 页面结构（从上到下）

1. 顶栏：仅供科研使用
2. 主图 + 标题 + 「Chat on WhatsApp」（主图是奶油底、银盖白标的 Tideora 瓶）
3. 四条信任条：24h 发货 / $500 免运费 / 付款前给 COA / 按盒销售
4. 品牌简介
5. 三个分类（GLP / 单肽 / 复配）→ 点击筛选下面的目录
6. **全部 30 款产品**：图片、名称、规格区间、包数、「Ask price」
7. 质检说明 + COA 样例图
8. 下单三步
9. FAQ（为什么没有价格、一盒是什么、能不能看 COA、怎么付款、发哪里、是不是人用）
10. 结尾 CTA + 底部常驻按钮

## 2. 客户点下去会发生什么

1. 点任意产品卡 → 请求 `/api/wa/next` 拿一个客服号
2. 直接跳到 `wa.me`，消息已经写好：

```
Hi TIDEORA — I'd like the price and availability for:

• Tirzepatide (5mg – 60mg, 9 packages)
Ref: LP-TIRZEP-8F3K

Please send the price list, the shipping cost to my country, and the batch COA.
```

客户只需要按发送。**Ref 码让客服一眼看出客户是从哪个产品点进来的**，不用再问。

3. 如果 2.6 秒没跳成功（桌面端、FB 内置浏览器、系统拦截），弹一张兜底卡片：显示号码 + 一键复制 + 再试一次。这一步是专门接丢单的，别删。

### 独立站其它页面也一样

`frontend/src/lib/waLink.ts` 在 `<body>` 上挂了一个点击代理，**任何** `href` 指向 `wa.me` 的链接都会被它接管：

1. 请求 `/api/wa/next` 拿号（和落地页同一套规则、同一个池子）
2. 把链接里的号码换成拿到的号，**消息内容一个字不动**
3. 计数记到实际打开的那个号上

所以首页浮动按钮、产品页询价、订单页「Pay via WhatsApp」都算进同一份统计，不需要给每个按钮单独埋点。

页面加载时就会先把这个访客的号码取好（"预热"），点下去是**同步跳转**，不用等接口——实测点击到跳转 38ms。接口挂了会依次退到 `/api/wa/public` 和静态快照，客户不会点了个死按钮，也不会被送去一个已经停用的号。

## 3. 号池怎么分流

`functions/api/wa/_shared.ts` 的 `pickNumber()`，顺序固定：

1. 只保留「启用」的客服号
2. 按国家过滤（`ALL` 或 `US`、`CA` 这类两位国家码，来自 Cloudflare 的 `cf.country`）
3. 去掉当天已达「每日上限」的号
4. 这个访客之前被分给过谁，就继续给谁（避免一个客户被两个客服接待）
5. 剩下的按「权重」随机
6. 全部到上限时仍然给号，只标记溢出——丢单比客服忙更贵

## 4. 后台怎么用

打开 `https://www.tideoralab.com/wh-admin`，输入管理口令。

| 想做的事 | 怎么做 |
| --- | --- |
| 加一个客服号 | 「添加客服号」填备注和号码（必须带国家区号，如 `12025550123`） |
| 今天不接这个号 | 点状态列切成「暂停」，立即生效 |
| 新号先试水 | 权重设 1，老号设 5–9 |
| 只接美国 | 国家填 `US`；其他国家会落到 `ALL` 的号 |
| 控制单人负荷 | 每日上限填 40 之类，超了自动分给别人 |
| 看哪个产品带来对话 | 「来源标记」面板，按次数排序 |
| 重新开始统计 | 「重置统计」，会一起清空来源标记 |

改完即时生效，**不用重新发布，也不用改广告**。

### 统计口径

后台只回答一个问题：**每个客服号接到了多少人。**

| 指标 | 含义 |
| --- | --- |
| 累计跳转 | 这个号从上线到现在，一共被点了多少次 WhatsApp 按钮 |
| 今日跳转 | 只算当天（UTC 零点换日） |
| 独立访客 | 点过这个号的不同浏览器数，同一个人点十次算 1 人 |
| 占比 | 该号累计跳转 ÷ 全部号累计跳转 |

顶部「独立访客」是**去重后的总人数**（一个人点了两个号只算 1 人），不是各行相加。

**覆盖范围是整个站**，不只是落地页：首页浮动客服按钮、产品页询价按钮、订单页「Pay via WhatsApp」、落地页所有 CTA，全部走同一套号池和同一套计数。站内其它页面的来源标记以 `SITE-` 开头，落地页以 `LP-` 开头。

浮动按钮**悬停显示的那个号码也是实时从号池取的**（`peek=1`，不计数），后台改号码 / 换启用号之后，最多 1 分钟或切回标签页就跟着变，不用刷新页面。改之前这里读的是写死的常量，所以后台怎么改都不变。

### 口令

口令存在 Cloudflare 的 Pages 密钥里，不在代码里，也不在仓库里。

- 当前口令：**`orGvx5tCs7Fklv5BVpZOzX-C`**
- 更换：`npx wrangler pages secret put WA_ADMIN_TOKEN --project-name tideora`
- 口令只存在当前标签页，关掉浏览器要重输；丢了重设即可，号池数据不受影响

### 发布

```bash
npm run deploy:cf
```

这条命令已经固定了 `--branch main`。**这一点很重要**：仓库当前分支叫 `frontend-only-cloudflare`，wrangler 默认会按分支名发到 Preview，线上不会更新。所以别自己敲 `wrangler pages deploy`，用这个脚本。

### 发布成功但线上没变（已遇到过一次）

症状：`wrangler pages deploy` 报 `Deployment complete`，但线上还是旧版本；部署别名 `https://<id>.tideora.pages.dev` 打开是 404。

原因在 Cloudflare 侧：Functions 发布那一步内部报错（API 返回 500 / code 8000000），项目状态被写坏，之后所有带 Functions 的部署都是空部署。

处理：

1. 不要继续重试，越试越乱
2. 用 API 回滚到最近一个能打开的部署：

```bash
# 列出部署，找到能打开的那个 short_id
npx wrangler@4 pages deployment list --project-name tideora
```

3. 等 Cloudflare 恢复后再 `npm run deploy:cf`

**判断方法**：部署完成后打开 `https://<新id>.tideora.pages.dev`，返回 200 才算成功；404 就是这次没发上去，线上仍是旧版本。

## 5. 广告怎么投

所有广告都指向同一个地址：

```
https://www.tideoralab.com/lp
```

可以带 UTM 参数，页面不解析，但广告后台能对上。老的分产品链接（`/lp/tirzepatide`）也不会 404，会落到同一个页面。

### 不接 Pixel

统计只在站内做，不依赖 Meta：客户每点一次 WhatsApp 按钮，`/api/wa/next` 记一次跳转并计入他实际被分到的那个号。广告后台的转化数据可以完全不看。

`frontend/index.html` 里保留了一段 Pixel 初始化代码，但 id 是空的，**不填就不上报任何东西**，不需要处理。

## 6. 基础设施（已经配好，不用再动）

| 项 | 值 |
| --- | --- |
| KV 命名空间 | `WA_POOL`，id `043fad68ccbc4b1a9f21caf9385bfa75` |
| 绑定 | `wrangler.toml` 里的 `[[kv_namespaces]]` |
| 密钥 | `WA_ADMIN_TOKEN`（Pages 生产环境） |
| 数据键 | `wa-pool` |

### 三个接口

| 接口 | 作用 | 要不要口令 |
| --- | --- | --- |
| `/api/wa/next` | 分配一个号，并记一次跳转 | 不要（客户调用） |
| `/api/wa/public` | 只返回**启用中**的号，不含任何统计 | 不要（兜底用） |
| `/api/wa/pool` | 读 / 写整个号池 | 要（`x-wa-token`） |

`/api/wa/public` 存在的意义：客户网络不好、接口超时时，页面还能拿到一份**当前有效**的号码列表。它只列启用中的号，所以停掉的号不可能从这里被发出去。

### 兜底顺序（从好到坏）

1. `/api/wa/next` —— 正常情况，顺便计数
2. `/api/wa/public` —— 分配接口挂了，用启用列表在本地按权重挑一个
3. 都没有 → 页面弹「客服正在接入 / 再试一次」，**不会**再退回任何写死的号码

第 3 层是有意的：以前这里还有一层构建时的静态快照 `wa-pool.json`，以及 `lib/api.ts` 里写死的 `WHATSAPP_NUMBER`。这两层都会在号池变化后过期，结果就是「后台停用了，站点还在把人往那个号上送」。现在这两个兜底都删掉了——宁可让客户点一次「再试一次」，也不能把他送到你关掉的号上。

所以：**号池里至少要有一个启用中的号**。全停用的时候后台会亮黄色告警，站点会显示提示卡。

### 配置和统计是分开存的

KV 里有两个键，这是修一个真实 bug 的结果：

| 键 | 内容 | 谁会写 |
| --- | --- | --- |
| `wa-pool` | 号码、启用状态、权重、国家、日上限 | 只有后台 |
| `wa-stats` | 点击、独立访客、来源标记 | 只有客户点击 |

以前两者在同一个文档里，每次点击都要「读整份 → 改计数 → 写整份」。KV 是最终一致的，于是一个早几百毫秒读到旧数据的点击请求，会把整份文档写回去，**把你刚做的停用又改回启用**。分开之后，点击永远碰不到配置。

只有当你要换 Cloudflare 账号、重建项目时才需要重做这些。

## 7. 已知限制

1. **KV 最终一致**：高并发下 `clicks` 可能少记一两次。用来判断"哪个号忙"够用，不要当财务数据。
2. **一个口令管全部**，没有分账号权限。多人运营时建议先各自用一个号，共用一个后台。
3. **粘性存在客户浏览器里**，换设备或清缓存会重新分配。粘性只记「聊过哪个客服」，不记号码本身——所以停用一个号，下一个点击就会换人，不用等缓存过期。
4. **全站按钮共用一套分配**，首页浮动按钮、产品页询价、订单页付款、落地页 CTA 都算进同一份统计。
5. **落地页不含购物车和结算**，这是故意的：这条路径只负责把对话开起来。
6. **商品数据来自 `frontend/src/data/catalog.json`**，改产品要重新构建发布。
7. 主图是 `frontend/public/images/lp-hero.jpg`，按官网产品图（银盖白标）生成。要换直接覆盖这个文件。

## 8. 本地开发

```bash
cd frontend && npm run dev
# 站点    http://127.0.0.1:3000/
# 落地页  http://127.0.0.1:3000/lp
# 后台    http://127.0.0.1:3000/wh-admin   ← 可以直接用，改的就是线上号池
```

`vite.config.ts` 把 `/api/wa` 代理到了 `https://www.tideoralab.com`，所以本地后台连的是**线上真实号池**：看到的统计、加的号，和线上是同一份数据。注意这一点——本地点「重置统计」会把线上统计一起清掉。

想指到别处：`WA_PROXY_TARGET=https://xxx.pages.dev npm run dev`。

其它 `/api` 仍然走 `API_PROXY_TARGET`（默认 `http://127.0.0.1:8080`，老 Go 后端，没起就 500，不影响号池）。

用 `npx serve frontend/dist` 这种纯静态预览时没有代理，后台会提示「本地预览只有静态页面」，落地页因为拿不到 `/api/wa/public` 会显示「客服正在接入」——这是正常的，不是故障。要看真实跳转就用 `npm run dev` 的 3000 端口，它带代理。
